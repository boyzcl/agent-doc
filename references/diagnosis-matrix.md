# 文档治理诊断矩阵

当项目文档已经出现协同摩擦时，先判断问题类型，再决定动作。不要一上来就扩写规范或全量重写。

## 1. 入口问题

判断信号：
- 新成员或 Agent 无法在 1 分钟内回答“先看哪里”
- 根入口只讲背景，不讲当前协作路线
- 有多个“总入口”，但没有主次关系

常见根因：
- `README.md`、`AGENTS.md`、`docs/index.md` 职责未分开
- 阶段性 handoff 临时变成事实入口
- 入口页把历史、执行、参考全塞在一起

优先动作：
1. 定一个主入口
2. 给其他入口降级成路由或辅助入口
3. 把“当前口径”与“背景材料”分开

## 2. Authority 问题

判断信号：
- 同一规则在多个地方都能找到
- runbook 和 convention 各有一版流程
- 大家用“最近更新”代替“谁说了算”

常见根因：
- 没有 `Source of Truth` 声明
- 入口层和规则层混写
- 文档创建时没有 topic ownership

优先动作：
1. 画 authority map
2. 给每个主题选一个主文档
3. 让辅助文档只保留链接、摘要或局部执行细节

## 3. 历史 / 证据混淆问题

判断信号：
- 设计演化史被当成当前设计说明
- 评测报告被当成操作规则
- archive 文档仍从主入口直接路由出去

常见根因：
- 没有单独的 history / archive 区
- 证据资产没有目录边界
- 当前规则没有稳定宿主，所以历史材料被迫代偿

优先动作：
1. 单独安放 history / archive
2. 单独安放 evidence / reports / artifacts
3. 在 authority map 里明确写出“可以参考，但不是默认规则源”

## 4. 范围失控问题

判断信号：
- 一次任务同时想改模板、目录、命名、校验、归档策略
- 还没完成一轮 pilot，就想强推全仓标准
- 规范文档增长速度大于真实使用反馈

常见根因：
- 没有 pilot 边界
- 把“可扩展”误解成“必须先定义完整”
- 没有区分项目本地问题和共享规范问题

优先动作：
1. 只选一个子系统或一个流程试点
2. 只给试点入口加最小校验
3. 把未纳入范围的目录显式写成暂不治理

## 5. 快速判定表

| 问题类型 | 先修什么 | 不要先做什么 |
| --- | --- | --- |
| 入口问题 | 根入口、文档索引 | 大规模补写下游细节 |
| Authority 问题 | authority map、topic ownership | 并行维护多份正式规则 |
| 历史 / 证据混淆 | 目录分层、边界声明 | 把历史文档全改成新模板 |
| 范围失控 | bounded pilot、忽略范围 | 一次性全仓治理 |
